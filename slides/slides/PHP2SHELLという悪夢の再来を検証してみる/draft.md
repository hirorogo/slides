### この話の「山」はどこか

速報記事はもう大量にある。**速さでは勝てないし、勝ちにいかない。**
この記事の価値は次の 2 点に置く。

1. **「誰が何を確定させたのか」を分離すること。**
   公式 PHP が言ったのは「2 件・critical・CVSS v4.0 9.2・23:00 JST リリース」**だけ**。
   CVE 番号も "RCE" も "Session Upload Progress" も、**公式は一文字も書いていない**（references #3）。
   世に出回っている見出しはほぼ全部が二次情報。ここを分けるだけで記事の信頼が立つ。
2. **「設定変更だけでは不完全」を、推測ではなくコードで示すこと。**
   php-src を読むと、multipart パーサ（`main/rfc1867.c`）は全ての multipart POST で無条件に走り、
   session 側のコールバックだけが `enabled=0` で早期 return する（references の「計測」）。
   **ここが独自パート。** 他の記事はここまでやっていない。

### 構成の道筋（slide → article 共通）

スライドは各節 1〜3 枚、記事は各節を増量＋技術補足。節番号はそのまま対応させる。

**1. つかみ：何が起きたのか**
- 10/20 に PHP 公式が「重大 2 件、23:00 JST に出す」と**予告だけ**した異常事態
- 予告より先に**リークが出てしまった**という順序の異常さ
- タイトル回収：「悪夢の再来」＝ PHP の RCE 祭りの既視感。ただし**今回はまだ中身が分かっていない**

**2. 公式は何を確定させ、何を言っていないのか** ←記事の背骨
- 公式予告の全文はほぼ 4 行。その 4 行に何が書かれていないかを列挙する
- **スコアが割れている**のが一番分かりやすい実例：公式 9.2 vs watchTowr CEO の "Both of them are CVSS10"
- 「確定／第三者の主張／リークの主張」の 3 分類表を 1 枚作る（PRD §2 がそのまま使える）

**3. Session Upload Progress とは何だったのか**（前提の技術解説）
- 本来の用途：アップロード進捗を `$_SESSION` に書く機能
- **効くポイント**：進捗はユーザスクリプトが走る**前**に書かれる ＝ アプリの認証より手前で動く
- 既定が **On** であること（ソースで確認済み）
- mermaid でリクエスト処理の流れ図（multipart POST → パーサ → コールバック → アプリ）

**4. php-src を読む** ←独自パート・ここを厚く
- 二次ソースが名指しした `php_session_rfc1867_callback()` は**実在する**ところから始める
- 2 層構造を図にする：
  - `main/rfc1867.c` のグローバルフック `php_rfc1867_callback`（**無条件に呼ばれる**）
  - `ext/session` が MINIT でそこに相乗り登録する
  - コールバック先頭の `if (!PS(rfc1867_enabled)) return;`
- → **「`enabled=0` で塞がるのは相乗りしている側だけ。パーサ本体は走り続ける」**
- ⚠️ ここで止める。「だから 2 件目はパーサにある」とは**書かない**（未確認・references #9）

**5. 緩和策はどこまで効くのか**
- Flatt の 10/21 14:00 追記（「攻撃自体は回避できない見込み」）を軸に
- 4 節のコード構造が、その追記の**機構的な裏付け**になっている、とつなぐ
- 対策を「根本（パッチ）／緩和（設定・WAF）／被害局限（最小権限・隔離・ログ保全）」の 3 段に分ける
- 「この設定を入れれば安全」と書かない。PRD §5 の方針どおり

**6. 検証環境で確かめる** ←sandbox の結果を入れる枠
- Docker 構成（compose.yaml / イメージのダイジェスト / php.ini 差分）を貼る
- **攻撃再現はやらない・載せない**（PRD §4.2）。やるのは正常系と構造の確認
- 入れるもの（sandbox 進行中。埋まり次第ここへ）：
  - [ ] `enabled` の既定値がビルド済みバイナリでも On か（`php -i | grep upload_progress`）
  - [ ] Session Upload Progress の正常動作ログ（$_SESSION に何が書かれるか）
  - [ ] `enabled=0` にしたときの正常系への影響（機能互換の確認）
  - [ ] mod_php と php-fpm で挙動差があるか（PRD D-06）
  - [ ] パッチ前後の同一条件比較（**23:00 以降**）

**7. パッチを読む** ←23:00 JST 以降に書く節
- 修正コミットの diff から根本原因を確定させる
- references の ⚠️/⬜ を ✅/❌ に更新してから書く：
  - 影響バージョン（5.4+ は**リークの主張**にすぎない）
  - 修正版番号（8.5.12 等は**未確認の推測**）
  - 原因が本当に `ext/session` 側だったのか、別の場所だったのか
- **予想が外れていたら、外れていたとそのまま書く。** それが一番おいしい

**8. まとめ：PHP 開発者が持ち帰れること**
- アプリ層の安全性（SQLi, XSS…）と**ランタイム層**の安全性は別物
- 自分のコードが 1 行も悪くなくても、**リクエストがアプリに届く前**に壊れることがある
- 「設定で回避」と「パッチで修正」を混同しない癖
- 分からないことを分からないまま運用判断する（＝ Embargo 中の動き方）
