## 執筆にあたっての方針

この記事の差別化ポイントは、速報の速さではなく、PHP2Shellを題材にPHP内部のメモリ管理やリクエスト処理を理解できることに置く。

単に既存の報告をまとめるのではなく、PHP公式の修正内容を読み解き、自分の検証結果を通して「なぜ問題なのか」「何を直したのか」「運用上どう対処すべきなのか」を説明する。

なお、現在は10月21日16時台（日本時間）で、公式の修正リリースは23時予定。パッチ公開後の内容を最終版に反映する必要がある。

最も深掘りする価値がありそうなのは、PHPのアプリケーションコードに到達する前の処理と、ランタイム内部のメモリ管理の関係。 ここまで説明できれば、単なる脆弱性紹介ではなく、PHPを使うバックエンドエンジニアにとって長く役立つ記事になるはずです。

なるほど、であればPRDはDockerを使った再現検証を中心とする構成に変更した方がよさそうですね。

単なるソースコード解析ではなく、実際にPHPをコンテナで動かして、脆弱なバージョンと修正版の挙動を比較する記事にします。

## PRDへの追加・変更事項

### 1. 検証環境

Docker Composeを使い、以下の環境をそれぞれ独立して構築する。

| コンテナ             | 目的                 |
| ---------------- | ------------------ |
| `php-vulnerable` | 修正前のPHPでの挙動調査      |
| `php-patched`    | 修正後のPHPとの比較        |
| `nginx`          | HTTPリクエストの処理・ログ観測  |
| `php-debug`      | PHP内部のエラーやメモリ管理の調査 |

PHP-FPMを基本構成とし、必要に応じてApache + mod_phpとの違いも調べる。

### 2. Docker環境の要件

- コンテナはローカル環境でのみ使用する。
- 外部公開ポートを設けない。
- ホスト側からのみアクセスできるよう制限する。
- 検証用のデータ以外はマウントしない。
- ホストのDockerソケットをマウントしない。
- 不必要なLinux Capabilityを付与しない。
- 検証が終わったらコンテナを破棄できる構成とする。
- 実際の再現コードについては、隔離環境内での原因分析と修正差分の確認を目的とする。

なお、Dockerだけで完全な隔離が保証されるわけではないので、可能なら専用のVM内でDockerを動かす。

- `compose.yaml`などのDocker構成

### 5. 記事の構成変更

記事のメインパートは以下の流れにする。

PHP2Shellとは何か → PHP内部の仕組み → Dockerで検証環境を構築 → 修正前の挙動を観測 → パッチ差分を読む → 修正版と比較 → 防御上の考察

この構成なら、読者がDocker環境の構築から結果の解釈まで追える、実践的な技術記事になります。

特に、\*\*「PHP-FPMとApacheで挙動が異なるのか」「設定変更とパッチ適用では何が違うのか」\*\*を掘り下げると面白そうです。PHP2Shell固有の問題だけでなく、PHPランタイム全体のセキュリティについても学べる内容にできます。
