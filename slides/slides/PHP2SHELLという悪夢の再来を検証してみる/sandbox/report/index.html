2攻撃チェーンの概要

今回再現したのは、次の鎖です。

  1. main/rfc1867.c の MULTIPART_EVENT_FORMDATA が PHP_SESSION_UPLOAD_PROGRESS の値を event_formdata.value として渡す。
  2. ext/session/session.c の php_session_rfc1867_callback() が progress->key = "upload_progress_" + 値 を作る。
  3. php_session_rfc1867_update() が php_session_initialize() → zend_hash_update() を実行し、アプリのスクリプトが動く前に sess_<PHPSESSID> へシリアライズして書き込む。
  4. php_session_rfc1867_early_find_sid() は Cookie / GET の PHPSESSID を先に読むため、攻撃者がセッションファイル名を選べる （session.use_strict_mode=0 の既定）。
  5. アプリに LFI があると、sess_<id> を include した瞬間に、 シリアライズされたキー文字列内の <?php ... ?> が実行される。

今回のラボでは、この「アプリ側 LFI」を lfi-demo/index.php に意図的に置いています。

4実験2: 既定 cleanup=1 のレース

session.upload_progress.cleanup=1 は、リクエスト終了時に進捗データを削除します。 しかし、アップロードを遅くすれば、終了前の window に LFI を間に合わせられます。 FPM の FILLUNIT=5120 を満たす初回チャンク（6000B）を送り、1.5 秒 stall しました。

5実験3: enabled=0 でも残る一時ファイル経路

session.upload_progress.enabled=0 の PHP-FPM（8089）では、 セッションへの進捗書き込みは止まります。しかし multipart のアップロード自体は続き、 $_FILES['f']['tmp_name'] は作られます。アプリがそれを include すると RCE になります。

10対策と限界

  • session.upload_progress.enabled=Off は、この session 書き込み primitive を止めるため、 今回の鎖には最も強い対策です。
  • cleanup=1 は終了時に消すだけで、アップロード中のレースには耐えません。
  • use_strict_mode=1 は SID を選ばせないだけで、progress の書き込みは続きます。 応答の Set-Cookie を読める状況では回避されます。
  • multipart の一時ファイルは enabled=0 でも作られます。 アプリがアップロードファイルを include する sink を持っている場合は別途遮断が必要です。
  • 本レポートの LFI 鎖は、アプリ側に LFI（またはセッションファイルを読む sink）があること が前提です。PHP コアだけで万能に RCE になる、という主張ではありません。
  • 公開 PoC のコア UAF / 公式 CVE の原因は、公式パッチ公開後に差分を確認する必要があります。
