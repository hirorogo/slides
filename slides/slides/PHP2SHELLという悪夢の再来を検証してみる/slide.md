# PHP2SHELLという悪夢の再来を検証してみる

tanahiro2010

## 今日話すこと

- PHPの重大脆弱性2件、何が起きたのか
- 公開PoCは本当に動くのか、自分のラボで確かめた
- わかったこと → 設定だけでは止まらない

---

## 何が起きたのか

- 10/20、PHP公式が「重大2件、10/21 23:00に出す」と予告だけした
- 予告より先に、SNSや研究者の間で中身がリークした
- タイトルの「悪夢の再来」は、PHPのRCE騒動の既視感

---

## 順序がおかしい

- 普通はパッチと一緒に詳細が出る
- 今回は中身が分からないまま先にリークが走った
- 「速報」ではなく「誰が何を確定させたか」を分けたい

---

## 公式が確定させたこと

- 2026-10-21 14:00 UTC にセキュリティリリース
- Critical 2件、いずれも CVSS v4.0 9.2
- 詳細・影響バージョン・修正版はリリース時に公開

---

## 公式が言っていないこと

- CVE-2026-109618 / 109619 という番号
- 「RCEである」という分類
- 「session.upload_progress が原因」という特定
- 影響バージョンも修正版番号も、公式はまだ何も出していない

---

## 情報が割れている

- CVE番号・原因・RCEは、全部リークと研究者発
- 重大度すら食い違う
- 公式 → CVSS 9.2 / watchTowr CEO → CVSS 10.0

---

## Session Upload Progress とは

- multipartのPOSTに特定のフィールドを入れると
- PHPがアップロード進捗をセッションに書く機能
- enabled の既定は On、cleanup の既定も On

---

## いつ動くのか

- アプリのスクリプトが走る前に動く
- PHPがPOSTを解析している最中に書かれる
- つまりアプリの認証より手前 → ここが最大のポイント

---

## php-src を読む

- main/rfc1867.c — multipartパーサ本体
- ext/session/session.c — 進捗コールバック
- sessionがパーサにフックして相乗りしている

---

## 設定で止まるのはどこか

```c
// ext/session/session.c
static int php_session_rfc1867_callback(...) {
    if (!PS(rfc1867_enabled)) {
        return retval;  // enabled=0 で止まるのはここだけ
    }
    // ... セッションへ進捗を書き込む
}
```

---

## 止まらないところ

- 早期returnで止まるのは session コールバック側だけ
- main/rfc1867.c のパーサ本体は設定に関係なく走る
- multipartの一時ファイルも残る

---

## 公開PoCの主張

- 2つの zval キャッシュが2回目の update で壊れる
- stale pointer が解放済みバケットを指す
- そこから zend_call_function → system() で RCE

---

## 自ラボで検証した

- PHP 8.4.4 / 8.5.4 を ASAN ビルドで用意
- PHP 5.6.40 も用意
- 公開PoC 618/619 をそのまま送信してみた

---

## 再現しなかった

- ASANレポートなし
- ワーカーの異常終了なし
- call先を毒アドレスにしてもクラッシュしない → 関数ポインタとして使われた形跡なし

---

## なぜ再現しないか

- post側の読み取りは初期化の前、解放はその後
- 解放されるのはセッションからデコードしたコピー
- 「解放済みバケットをstale pointerが読む」順序になっていない

---

## 公開PoC自身も認めている

- 同梱の VALIDATION.md に「ASAN crash はローカルで未観測」
- ツイート画像は機構説明のスクショ、実行証跡ではない
- 「再現しなかった」＝「CVEが存在しない」ではない

---

## でも別の鎖は成立した

- コアのUAFは再現しなかった
- 一方で session.upload_progress の書き込みは強力な primitive
- アプリ側にLFIがあると未認証RCEまで届いた

---

## multipart + LFI の流れ

- 攻撃者が PHPSESSID を決める（use_strict_mode=0）
- 進捗フィールドにPHPコードを入れる
- PHPがアプリ実行前に sess_ ファイルへ書く
- アプリのLFIがそのファイルを include して実行

---

## 実測結果

- cleanup=0 のLFI → uid=33(www-data)
- enabled=0 + 一時ファイル include → uid=33(www-data)
- mod_php でも → uid=33(www-data)

---

## cleanup=1 でも止まらない

- 終了時に消すだけなので、アップロードを遅くすればよい
- 初回チャンクを満たして 1.5 秒 stall させる
- その間にLFIを叩くと 3/3 で成立した

---

## enabled=0 でも残るもの

- session書き込みは止まる
- multipartのアップロードと一時ファイルは残る
- tmp_name を include する sink があれば別経路でRCE

---

## use_strict_mode=1 でも

- SIDを選ばせないだけ
- 進捗の書き込み自体は続く
- 新しいSIDは応答の Set-Cookie に出る → 読めれば追従できる

---

## 共有された影響調査レポート

- 対象は PHP 5.6.40 のWebアプリ（EOL、公式修正の対象外）
- 露出条件は揃っていた
- ただし「RCE確認」ではなく「成立した場合の影響評価」

---

## 緩和策の強弱

- enabled=Off → session primitive は止まる / 一時ファイルは残る
- use_strict_mode=1 → SID固定は防ぐ / Set-Cookie追従は残る
- パッチ → コアの原因 / アプリ側LFIは残る

---

## パッチ後に確定すること

- 公式のCVE番号・影響バージョン・原因・攻撃条件
- 修正コミットのdiffがどこを直したか
- 公開PoCの主張が正しかったか → 間違いなら隠さず撤回する

---

## 持ち帰れること

- アプリ層の安全性とランタイム層の安全性は別物
- 自分のコードが1行も悪くなくても、届く前に壊れることがある
- 「設定で回避」と「パッチで修正」と「sinkの除去」を混同しない

---

## まとめ

- 何が起きたのか → 中身が分からないまま先にリークが走った
- 公開PoCは動くのか → コアのUAFはそのままでは再現せず
- わかったこと → multipart primitive + アプリ側LFI の鎖は成立した
