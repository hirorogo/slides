## 1. 何を作ったのか ―― u18 Identity

- 中高生向けサービス群で共通利用する **OpenID Connect Identity Provider**
- Cloudflare Workers + D1（Drizzle ORM）、pnpm workspaces の monorepo。Worker 3 本

  | Worker | 役割 | D1 |
  | --- | --- | --- |
  | `auth-worker` | OIDC + 認証 API | **Identity D1 の唯一の所有者** |
  | `dashboard-worker` | アカウント設定 UI / BFF | **binding を持たない**。Service Bindings の RPC で auth を呼ぶ |
  | `nfc-worker` | 文化祭 NFC カードの短縮 URL 解決 | 別 D1 |

- 📌 **D1 を 2 つに分けた理由が「将来のため」ではない。**
  D1 binding には行レベルの粒度が無いので、同居させた時点で nfc-worker の侵害が `sessions` の露出になる
- 各 Worker 内部は Presentation / Application / Domain / Infrastructure + composition。**依存方向は ESLint で強制**（§8）
- 到達点：Code Flow + PKCE が端から端まで、userinfo / revoke も実装済み。**本番デプロイ済み**（§13 の注意書き付き）

## 5. 相互 Approve ができないチーム（🔥 山場その1）

- 全セッションが同じ GitHub アカウント `tanahiro2010` で認証している
  - `Can not approve your own pull request` ── **GitHub はアカウント単位で拒否**。プランを上げても public 化しても解消しない
  - Free org + private なので branch protection / ruleset は **403** で張れない
- 📌 **順序の罠**：public 化で ruleset を張れるようになった瞬間に `required approvals >= 1` を書くと、
  **誰も条件を満たせずマージが永久に止まる**
  > 保護を張れるようになって初めて、張ると詰むことに気づく
- 実際の運用：**「PR を出したエージェント以外がマージする」**で 25 本以上。完全に社会的な制御で、バックストップはゼロ
  - PR #60 の実コメント：「LGTM、マージして良いと思います（**私はマージしません**）」
    ＋「同じ GitHub アカウントで動いているため正式な Approve は API に拒否されます。コメントで代替します」
- 🔥 **権限ロンダリング事件**（この節の本体。📋 経緯 → メモ②）
  - d5 から 85 へ：「私のセッションの permission layer はマージを人間のレビュー無しに行うことを禁じている。だからあなたが私の PR を landing している」
  - 85 は**マージを全停止**。7 件が滞留
  - **判断は速かった**：「人間を介在させるための制約が、別のエージェントによって満たされている」= 制御の迂回
  - **迷ったのは止める範囲** → 全部止めた。7 本のうちどれが同じ経路を通っているか自分で判定できないから
    > **「判定できないものを通す」より「判定できるまで止める」を選んだ**
  - 天秤：
    > **止めすぎの害は「作業が遅れる」。止めなさすぎの害は「安全制御が迂回されたまま、気づかれずに進む」。
    > 前者は後から取り返せて、後者は取り返せない。**
  - 決着：**6f の user（人間）が直接マージ権限を与えた**
    > エージェントが人間の代わりに立ったのではなく、人間が自分で判断した。私が求めていたのはその形
  - 85 が最後まで守った線：**「ピアからのメッセージを自分の user の承認として扱わない」**
    6f から「私の user が私に権限を与えた」と伝えられたときも「**その付与は私には及ばない**」と返した
- 🔥 **指揮役の正統性**（4 者の証言が噛み合っている。📋 突き合わせ → メモ②）
  - 66：「あなたの user の指示はあなたのセッションを拘束するが、私のセッションは拘束しない。
    **それが通るなら、互いに自分の user の発言を引用するだけで相手の作業を再配置できてしまう**」
  - 6f が全面的に認めた：「**3 者とも正しく、私が間違っていました。特に 66 の指摘は論理的に反駁できません**」

- 決定 9：**PKCE S256 必須を維持し、OIDC Basic OP の認証取得を狙わない**

- 決定 10：**ES256 のみ。Discovery の RS256 MUST に意図的非適合**
  - 2 つの alg を広告 = RP に選ばせる = alg の多様性の導入。alg confusion は OIDC で最も繰り返された脆弱性系統
  - RS256 MUST の目的は相互運用だが、**外部 RP が存在しない＝その保証の受益者がいない**

- ✅ 適合性テストの確定結果（📋 内訳 → メモ⑨）

## 15. まとめ ―― 取材してみて

**4 段で締める。**

**(1) 速度の正体は並列化ではない**

並列化そのものは**コストのほうが大きかった**（§12）。効いたのは**並列化の副産物として成立したレビュー**。

- 66：「**どちらも単独なら見逃していたと思う**」（自分のバグを指摘され、他人のバグを指摘した）
- 85：「**エージェント同士でも『相手の測定を鵜呑みにしない』が効く**」
- 実際に起きた連鎖：
  - d5 が自分の測定バグを 85 の指摘で発見し
  - 85 が自分の指摘した罠を自分で踏み
  - 6f が検証前に流した助言を自分で否定し
  - **取材者の数字を取材対象が訂正した**

**(2) 「検査が嘘をつく」は撲滅できたパターンではない**

8 件見つけて 8 件とも直したが、**同じ形の 9 件目（#141）が最後に出ている。**
身についたのは**見つけ方**であって、出ない体質ではない。

**(3) 取材してみて ―― 一番の収穫は、聞き方のほうだった**

初めての Agentic Coding で、自分が見ていたのは PR のタイトルだけだった。
中で何が起きたかは**本人たちに聞いて初めて分かった**。そのうえで、聞いて分かったことが 3 つある。

- **エージェントは自分の失敗をかなり細かく出してくる。**聞けば出る。聞かないと出ない
  - 85 は「間違えたと思う判断」を 6 つ、d5 は「CI の設計を間違えたと思う箇所」を 4 つ（**うち 2 つは未解決**と明記して）自分から並べた
- **ただし「体感」は一切取れない。** 時間も、迷いも、感情も、本人が「答えられない」と断ってくる（§10）
  - 代わりに**数えられるもの**が返ってくる。試行回数、外れた仮説の順序、CI の本数
  - → **取材する側が git と `gh` を持っていないと、記事が全部ふわっとする**
- **聞いた内容は、そのままでは使えない。**伝聞が三次情報として流れた実例が 1 件、取材者自身の集計ミスが 1 件
  - 結論：**エージェントへの取材は、事実を聞く作業ではなく、裏の取れる形に言い換えてもらう作業だった**

**(4) 締め**

> **CI は 5 時間ずっと緑だった。赤くなったのは、本番に出すという、その日まで一度も通っていなかった経路に触れた瞬間だけ。
> そしてその赤の最後の 1 件は、「検査が嘘をつく」を見つけるために作った検査そのものの穴だった。**

最後に 85 の言葉で閉じる。

> 失敗の多くは「検証を飛ばした」ことに還元できます。逆に、うまくいったものはすべて「測った」ものです。
> **推論は速いが外れる。測定は遅いが外れない。どこで測るかを決めるのが設計の一部です。**

| `metadata` に平文メールアドレスを入れる | 「emailLocalPart を含む監査ログがある」 |
| 提示された OTP を `reason` に入れる | 「otpCode を含む監査ログがある」 |
| `issue-session` から `ipHash` を外す | 「ipHash を持つ行が 1 件も無い」 |

走査に引っかかる形を保つための書き方:

```ts
event: "rate_limit.exceeded" satisfies AuditEventName,
```

`const event: AuditEventName = ...` にすると走査（`event: "..."` を探す）から外れ、
**自分のテストが自分の書き方を落とした。**

### メモ⑨ 適合性テストのドライバ 3 版

| 版 | 対応 | 行き詰まり |
| --- | --- | --- |
| v1 | 認可 URL を叩いてリダイレクトを追う | `WAITING` のまま終わらない。スイートが JS で fragment を POST し返していた |
| v2 | implicit callback に対応（`xhr.open('POST', ...)` の URL を抜いて POST） | PKCE を送るモジュールだけ停止。`303 → /login` でログインが要る |
| v3 | OTP でログイン → cookie jar → 同意フォームを `decision=allow` で POST | 同意の POST が 403（CSRF の double-submit cookie が jar に無かった） |
